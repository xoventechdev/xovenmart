# Bot migration recovery (2026-09-19)

## What happened

The first push of the bot migration tried to extend the `order_source`
enum with `MESSENGER` / `WHATSAPP_CLOUD` / `WHATSAPP_GREEN` AND create
the new tables / columns in a single migration file. Prisma's
`migrate deploy` ran into Postgres's "ALTER TYPE ... ADD VALUE cannot
run inside a transaction block" error. The migration row was left in
`_prisma_migrations` in a **failed** state, blocking every subsequent
`migrate deploy`.

## What's in this commit

The fix is two migrations (the enum-extension one is auto-marked
non-transactional by Prisma because it only contains
`ALTER TYPE ... ADD VALUE`; the schema one is plain transactional DDL):

- `20250919_bot_order_source_enum/` — only `ALTER TYPE` statements
- `20250919_bot_schema/` — all the column-adds + new tables

The previous failed migration directory `20250919_bot_phase1/` was
removed from the repo so Prisma doesn't try to re-apply it.

## Operator recovery (run once on the VPS)

SSH in and run these from `/var/www/xovenmart/api/shared` (where the
production `.env` lives):

```bash
# 1. Mark the failed migration as rolled-back so Prisma doesn't
#    refuse to apply the new ones. This DOES NOT touch the DB schema
#    — it only clears the `_prisma_migrations` row.
docker compose exec api \
  pnpm --filter @xovenmart/db exec prisma migrate resolve \
    --rolled-back 20250919_bot_phase1
```

(If `20250919_bot_phase1` partially applied on the prod DB — the
schema columns/tables may or may not be there — Prisma's resolve will
just clear the failed row. Then the new two migrations below will
re-apply anything that's missing. The DDL is idempotent thanks to
`IF NOT EXISTS` on the enum values and the implicit `ADD COLUMN`
"already exists" handling on subsequent runs.)

```bash
# 2. (optional) Confirm the failed row is gone:
docker compose exec postgres \
  psql -U xovenmart -d xovenmart \
    -c "SELECT migration_name, finished_at IS NULL AS still_running, applied_steps_count FROM _prisma_migrations ORDER BY started_at DESC LIMIT 5;"

# 3. Re-trigger a deploy in Coolify. The new migrations will apply:
#    - 20250919_bot_order_source_enum (non-transactional, ADD VALUE x3)
#    - 20250919_bot_schema (transactional, columns + 3 tables)
#
# If the old failed migration left the bot_* tables / columns in place
# on the prod DB, the new migrations will skip them via Postgres's
# "already exists" error (Prisma's default migration wrapper would
# normally catch this — but `ADD COLUMN` and `CREATE TABLE` both raise
# `already exists` if you re-run them, so the migration will fail
# again. If that happens, see "Cleanup SQL" below.)
```

## Cleanup SQL (only if migrate deploy still fails after step 1)

If the half-applied migration left some but not all of the new
columns/tables on the prod DB, the new migration may complain about
"already exists". Connect via psql and check:

```bash
docker compose exec postgres psql -U xovenmart -d xovenmart -c "\d orders" | grep -E "bot_"
docker compose exec postgres psql -U xovenmart -d xovenmart -c "\d products" | grep bot_visible
docker compose exec postgres psql -U xovenmart -d xovenmart -c "\dt bot_*"
```

If any of these exist, the old failed migration actually applied
partially. The new migration would re-try to create them and fail
with `42P07` (duplicate_table) or `42701` (duplicate_column).

The cleanest recovery in that case is to manually mark the new
migrations as applied in `_prisma_migrations` and let the bot code
work with whatever partial schema exists:

```bash
# Insert a "successful" row for each new migration so Prisma thinks
# they already ran:
docker compose exec postgres psql -U xovenmart -d xovenmart -c "
INSERT INTO _prisma_migrations
  (id, checksum, migration_name, finished_at, applied_steps_count, logs)
VALUES
  (gen_random_uuid()::text, '', '20250919_bot_order_source_enum',
   NOW(), 1, 'manually marked applied after partial prior failure'),
  (gen_random_uuid()::text, '', '20250919_bot_schema',
   NOW(), 1, 'manually marked applied after partial prior failure');
"
```

(Prisma records a `checksum` per migration; if you need to bypass the
checksum too, use `UPDATE _prisma_migrations SET checksum = '' WHERE
migration_name LIKE '20250919_bot_%';` first. The empty checksum
bypasses Prisma's "did the migration file change?" check.)

If even the partial application didn't happen (i.e., the failed
migration rolled back completely), the new migrations will apply
cleanly — no cleanup needed.

## Verification after deploy

```bash
# Migration table should now show the new rows as finished:
docker compose exec postgres psql -U xovenmart -d xovenmart -c "
SELECT migration_name, finished_at IS NOT NULL AS done
FROM _prisma_migrations
WHERE migration_name LIKE '20250919_bot_%'
ORDER BY started_at;"

# New tables exist:
docker compose exec postgres psql -U xovenmart -d xovenmart -c "\dt bot_*"
# → bot_conversations / bot_events / bot_idempotency

# Enum extended:
docker compose exec postgres psql -U xovenmart -d xovenmart -c "
SELECT enum_range(NULL::order_source);"
# → {WEB,ANDROID,POS,MESSENGER,WHATSAPP_CLOUD,WHATSAPP_GREEN}
```
